# 当前蓝队算法完整说明

本文以仓库**当前实际接入评测的代码**为准，描述蓝队从传感器输入到控制命令输出的完整过程。它是一套多机协作的规则式算法，不含神经网络训练或推理；文中的“安全”“最优”均指算法基于**本机已观测信息**作出的判断，不代表掌握地图真值，也不保证全局最优或绝对无碰撞。

代码基准：`src/swarm_rescue/solutions/my_drone_eval.py` 在 `rescue` 模式下返回 `MyDroneBlueAdvanced`；该类继承 `MyDroneBlueBasic`，后者再继承官方示例 `MyDroneRescueExample`。因此，阅读一个行为时要同时留意子类覆写与父类继承的方法。仿真物理、抓取碰撞和评分不由这些蓝队控制器实现。

## 1. 一句话概括与总体结构

无人机先估计自身位姿，用 Lidar 建立本机占据栅格；没有炸弹任务时优先去“已知可达区域与未知区域的边界”探索；发现炸弹后通过队友通信和成本报价减少重复追逐；抓住炸弹后优先走已知安全的 A* 路线返回，必要时退回沿来路返航；最后在处置区表面保持抓取，直至炸弹实际被仿真销毁。

单步控制的实际结构为：

```text
GuiSR.on_update()
  ├─ 收集各机 define_message_for_all() 的广播
  ├─ 依次执行各机 control()
  │    └─ MyDroneBlueAdvanced.control()
  │         ├─ GPS / 指南针 / 里程计 → 位姿融合
  │         ├─ 定期 Lidar / 语义扫描 → 本机占据栅格
  │         ├─ MyDroneBlueBasic.control() → 任务状态机
  │         │    ├─ carry：携弹返航及处置
  │         │    ├─ chase：追逐当前可见炸弹
  │         │    ├─ navigate：去往已记忆炸弹
  │         │    └─ explore：寻找新区域
  │         └─ 双机抢弹检查 / 局部交通避让 / 健康限速
  └─ 将每架无人机返回的命令交给 playground.step() 执行
```

上面“收集广播”发生在本轮控制调用之前；通信可能有距离限制、延迟或被禁用，所以控制器不能假设队友信息始终新鲜。

## 2. 输入、输出和内部记忆

### 2.1 允许使用的输入

- GPS、指南针：提供带噪声的世界坐标和机头朝向，也可能暂时失效。
- 里程计：提供短时间位移与角度变化，用于 GPS 缺失时继续推算。
- Lidar：提供多方向距离及相对射线角度，用于建图和近场避障。
- 语义传感器：识别可见的炸弹、无人机、处置区等，以及相对角度、距离和 `grasped` 状态。
- 通信消息：提供队友的目标声明、发现的炸弹、处置区、位姿、是否携弹、目标报价及探索目标。
- 本机状态：`grasped_bombs()`、健康值、奖励、无人机编号、地图尺寸和已执行步数等。

控制器不在 `control()` 中读取地图真值、炸弹全局列表或真实位姿。`MyDroneBlueAdvanced` 通过覆写 `measured_gps_position()` 与 `measured_compass_angle()`，使继承来的导航与语义坐标换算使用**融合后的位姿**；采集原始测量时则显式调用父类方法，避免循环读取自身估计。

### 2.2 控制器输出

每架无人机每次 `control()` 返回一个 `CommandsDict`，包含：

```python
{
    "forward": 0.5,   # 机体前后方向，通常在 [-1, 1]
    "lateral": 0.0,   # 机体左右方向，通常在 [-1, 1]
    "rotation": 0.2,  # 转向命令，通常在 [-1, 1]
    "grasper": 1,     # 1 为尝试/保持抓取；0 为松开
}
```

数值只是格式示例，不是固定输出。控制器输出后，移动、关节抓取、碰撞、血量和炸弹销毁由仿真执行。**碰到炸弹并不等于必定抓取成功**；本算法必须主动设置 `grasper=1`，并用后续的 `grasped_bombs()` 确认。

### 2.3 每机维护的状态

每架无人机都有独立的位姿滤波器、占据栅格、路径规划器、前沿探索器、交通协调器和返航器。还维护最近看到的炸弹、队友声明、处置区位置、出生点、探索轨迹、当前任务目标及短时路线缓存。

目前**没有把各机完整的占据栅格合成一张全队共享地图**。广播的是少量目标与任务信息，而不是每个栅格的占据状态。因此，一架无人机知道某处有炸弹，并不代表它也拥有另一架无人机在那附近扫描出的安全通路。

## 3. 每一步的详细执行顺序

以下步骤以 `MyDroneBlueAdvanced.control()` 为入口；其中父类状态机仍在中间执行。

1. 取下一步编号，读取原始 GPS、指南针和里程计，调用 `LocalizationManager.update()`。如果滤波器判定发生重新定位，清空依赖旧坐标系的地图、路径、炸弹及处置区记忆，避免把新旧坐标混用。
2. 当 `step % 5 == 1` 且位姿有效时，读取 Lidar 和语义结果，尝试更新本机占据栅格。这里“每五步”只限制建图；位姿更新、任务控制与近场传感器使用仍是每步进行。
3. 比较本步与上一控制步的 `grasped_bombs()`：刚抓住时保存本次奖励基线并初始化返航轨迹；刚失去携弹状态时检查奖励是否增长，用于区分“真正处置”与“意外脱落”。
4. 调用 `MyDroneBlueBasic.control()`：接收队友消息、解析语义目标、更新记忆与稀疏来路轨迹，再按 `carry > chase > navigate > explore` 的优先级调用相应处理器。动态分派使高级类覆写的探索、追弹、返航和移动方法实际生效。
5. 对父类得到的命令做最后修正：如果两机误抓同一弹，高编号机停下并松爪；空载机靠近队友已抓住的弹时关闭抓取；遇到迎面队友或自身卡住时执行让行/脱困；低血量时限制前进速度。
6. 返回四个执行器命令，等待仿真执行。下一步再根据新传感器读数和奖励反馈调整。

父类 `MyDroneBlueBasic.control()` 的任务选择可简化为：

```text
如果已携弹 → carry
否则若存在可认领的可见炸弹 → chase
否则若存在可认领的历史炸弹坐标 → navigate
否则 → explore
```

这不是一次性生成整局飞行轨迹，而是**每步重新观察、必要时改目标或改命令**的闭环控制。

## 4. 位姿估计：GPS、指南针与里程计

`blue_team/localization.py` 用三状态滤波器维护世界坐标 `(x, y)` 和朝向 `heading`，同时估计位置与朝向的不确定性。首次初始化需要同时获得 GPS 和指南针；如果从出生开始就没有任何世界坐标观测，算法不会凭空构造全局位姿。

初始化后，每步先按里程计预测位姿。GPS 或指南针可用时，以受限频率进行校正：两者正常校正都至少间隔 8 步，并拒绝与预测明显不符的离群值。若连续 GPS 读数一致但与旧坐标偏差较大，滤波器可以重新锚定；此时高级控制器清空旧世界坐标记忆。

位姿过于不确定时，前沿选择和建图不会继续把其视作可信全局位置；携弹时则保留抓取，低速尝试局部 Lidar 避障，以期走出传感器失效区域。无 GPS 区域的里程计推算只是短期后备，误差会增长，不能保证长期精确定位。

## 5. 本机占据栅格与安全路线

`blue_team/occupancy_grid.py` 把世界划成默认边长约 20 像素的栅格。每格状态为：

- `UNKNOWN`：尚未被充分证实；
- `FREE`：扫描证据支持可通行；
- `OCCUPIED`：障碍物或短期动态占据。

Lidar 射线经过的格子增加自由证据，射线终点可能增加障碍证据。(每个格子的初始证据为0，状态为UNKNOWN，射线经过的途径格每次更新证据-0.35，命中大于三次+1.2，小于-0.62则更新为FREE，大于0.85设置为OCCUPIED（每控制器的五步更新一次）)对静态障碍，不是单次命中就永久标为墙；对被语义结果识别为无人机或炸弹的目标，采用短期动态占据，避免把可移动物体永久写入静态地图（语义传感器识别为drone或炸弹会将其设定为一个固定步数的OCCUPIED，后面变成FREE）。处置区表面也不会被当成普通墙处理。（目前并不会将某个区域永久设置为墙）（当前雷达ruguo检测到了处置区，会计算目标坐标后面再逐渐更新并通知其他wurenji）(或许可以建立一个永久的处置区地图)

`check_segment(start, end, clearance, step)` 会沿线段及其周围的安全余量检查格子，返回 `SAFE`、`UNKNOWN` 或 `BLOCKED`。只有整段已知自由且满足余量，才称为“已验证安全”；未知区**不会**因为没有观察到墙就自动变成安全捷径。

`blue_team/path_planner.py` 先尝试已验证的直线通路，必要(check没有得到safe)时在已知安全格子上运行有扩展上限的八邻域 A*(对于路径上的每个安全格，计算起点走到该点的累计代价和该点到目标点的估计距离，选取代价小的)，禁止斜穿障碍角，并对高风险邻格增加代价。找到路线后，只有逐段 `check_segment()` 通过才会压缩折线。若目标表面本身不可站立，可在其附近寻找安全代理格；规划仍可能返回“目标被挡”“起点被挡”“无路”或“预算耗尽”。

规划器只解决**当前本机已知地图**上的问题；为了探索未知区域，导航层在没有已验证路径时仍可能尝试沿目标方向缓慢推进，并由局部 Lidar 避障。这是探索所需的折中，不是“所有移动都已通过 A* 安全证明”。

每架无人机有一个自己的栅格地图（共享高置信度的静态障碍和已探索区域?）

## 6. 无炸弹任务时：多机探索
(没有携弹，没有可追踪的炸弹，mode设置成explore)
高级探索器 `FrontierExplorer` 优先寻找“本机已知可达的自由格，且旁边仍有未知格”的前沿。它把前沿分组，挑选多个候选点，用以下因素排序：

- 候选点附近的未知区域数量，即可能带来的探索增益；
- 路程、附近障碍风险和切换当前目标的代价；(越危险或许越应该探索?)
- 与本机编号分配的横向区域是否吻合；
- 队友广播的探索目标是否已经覆盖同一区域；
- 对远征无人机，朝地图远侧推进的收益。

候选点必须先满足可达（类似于队列BFS）及安全余量条件，再用限额 A* 验证（对有限的格子做A*验证）路线。前沿目标短期保持，避免每步抖动；到达或长期无进展的目标会暂时冷却，防止在同一片已探区域反复徘徊。候选目标选择只保证局部启发式效果，**不保证整个地图无遗漏或最短时间覆盖**。

当地图证据不足、位姿不可信、前沿找不到可达目标时，退回 `MyDroneBlueBasic` 中的 `ExplorationManager`：按编号将地图横向分区，每机沿自身区域的蛇形覆盖路点巡航。如果这种世界坐标巡航也不可用，才退回官方示例的局部直行/转向式探索及 Lidar 脱困。因此“当前每架无人机都只走一条蛇形线”并不准确；蛇形只是后备层。

在 10 机配置下，编号 6–9 的无人机被指定为远端侦察机。它们在仍靠近出生区的赶路阶段，通常只响应距离不超过 70 像素的炸弹，以减少所有无人机都在近处停下；离开这一阶段或到达远端后恢复正常追弹。其他无人机正常选择可认领目标。这个分工可能提升右侧覆盖，但也可能暂时放过沿途较远的炸弹，应以多轮回收率检验。

## 7. 炸弹观测、记忆与多机任务分配

语义传感器可能对同一炸弹给出多条命中射线。控制器将相近的表面坐标聚成一个候选，保存短期炸弹记忆；已被抓住或近期确认清除的炸弹不再当作新目标。可见目标暂时消失时可以按记忆导航，而不是立刻重新随机探索。到达记忆坐标附近却看不到炸弹，会短暂原地扫描；连续找不到后放弃过期目标。

每机广播包含编号、位置、模式、是否携弹、当前目标声明、最近一次本机炸弹观测、近期清除目标、处置区、朝向、探索目标和报价。广播**不是**把所有炸弹记忆或整张地图一次发出去。炸弹记忆、目标声明和消息都有限时；通信丢失时各机仍可独立搜索，但协调效果下降。

`CostAllocator` 为候选炸弹给出 0–1000 的相对成本报价，考虑本机到炸弹的距离、估计返航距离、健康、附近风险、位姿不确定性和切换目标成本。报价只用于**比较哪架机更适合接单**，不是实际要执行的路径；为避免高计算成本，报价不为每个目标都调用完整 A*。

如果队友已经携弹，本机不再争该目标；否则成本明显较低者优先，报价相近时按无人机编号稳定决胜。这里是通信可达范围内的**分布式局部仲裁**，不是全队实时集中式最优匹配。通信延迟、同一炸弹的测量位置偏差和传感器失效仍可能造成重复接单。

## 8. 追弹、接近和双机误抓处理

可见目标进入 `chase` 后，控制器保持 `grasper=1`，根据目标相对角度连续给出前进、侧移和转向命令。近距离不再要求机头先旋转到极小角度才移动，避免在炸弹旁只转圈不接近；较远时结合 Lidar 对前方障碍降速、转向或脱困。

仅知道历史世界坐标时进入 `navigate`，规划已知安全路线或在 Lidar 保护下向目标推进，靠近后靠语义传感器重新捕获目标。纯 `explore` 阶段不常开抓取器，避免路过时误抓队友已经搬运的炸弹；即使追弹/导航阶段抓取器已打开，只要近距离看到被抓住的炸弹或确认队友正携弹，也会临时关闭本机抓取命令。

仿真仍可能让两架无人机几乎同时抓住同一炸弹。高级控制器会利用近期的目标声明和队友位置核对；若判断两机附着同一目标，**较大编号无人机输出停止移动和 `grasper=0`**，让较小编号机继续搬运。该规则依赖可用且足够新鲜的消息，不能保证覆盖所有极端场景。

## 9. 抓住后：A* 返航、来路后备、精确处置

确认已携弹后，任务优先级立即变成 `carry`，始终保持 `grasper=1`。已观测到处置区时以其记录位置作为返航目标；否则先往出生点附近返回，进入语义探测范围后再改用实际观测。控制器**没有硬编码 Map01 处置区坐标**。

返航优先级如下：

1. 在本机已知安全的占据栅格上，以约 45 像素的携弹安全余量规划 A*，缓存路径，并逐步检查当前路段；目标或地图显著变化、路径过期、路段被新障碍阻断时重规划。
2. 如果当前地图无法给出已验证路线，沿探索期间记录的稀疏“面包屑”轨迹逆行；只有能证明整段自由的地方才跨越多个轨迹点，已验证可直接连接的回环可删除。
3. 两者都不可用时，以处置区或出生点为大方向继续进行局部 Lidar 保护下的移动。

所以当前算法**不是单纯原路折返**，也不是知道全图后的全局最短路。A* 可能因为地图未知或安全余量过大而找不到路线；轨迹后备是为了在长墙或地图不完整时仍有可循路径。

接近处置区后，控制器从多条语义射线的命中点估计一块较稳定的**处置区表面**，而非假设这些点就是区域中心。距离表面足够近时进入精确投放：先向表面推进，接近边界后保持抓取并原地旋转，使关节连接的炸弹扫过处置区；若未成功，下次换表面位置重试。**不会因旋转了固定步数就主动松爪**。仿真报告炸弹被销毁后，`grasped_bombs()` 会变为空，控制器再结合本次携弹期间奖励是否增加，确认是否真的完成处置；若只是脱落，则不广播“已清除”。

## 10. 交通避让、脱困与健康保护

`TrafficManager` 综合队友广播、语义检测、Lidar 和里程计判断局部冲突。携弹机优先；空载机迎面相遇时按编号稳定让行。让行时优先向 Lidar 显示开阔的一侧侧移，空间不够则后退或转向。若约 24 步没有有效净位移，会触发限时脱困。接近处置区正在执行投放动作时，不插入一般交通让行动作，避免打断投放。

这一套是局部反应式规则，并不能证明密集交通场景永不死锁。特别是通信不可用、队友位置过期或狭窄通道被多机占据时，仍可能出现拥堵。

健康值作为软约束：健康极低时不再接新的炸弹任务；健康下降时限制部分前进速度。它**没有实现“低血量立即退出任务并独立返航”的完整策略**，携弹任务仍优先。安全余量与局部避障也不能保证健康值始终不下降。

## 11. 计算量控制：为什么仍可能很慢

早期计时曾显示，耗时主要在探索时的 A* 与大量线段安全检查，而非物理引擎。当前代码使用了多层预算和缓存：

- 建图每五步尝试一次，而不是每步全量处理全部射线；
- 前沿先用便宜的直线距离与收益上界排序，再对有限候选运行 A*；有可行目标时通常最多规划 6 个候选，否则最多尝试 12 个；
- 前沿单次 A* 的扩展上限为 350；普通导航为 500；携弹返航为 3500；
- 同一步、同一地图版本复用格子安全与风险结果；静态安全余量偏移也缓存；
- 普通路线有最长约 60 步的定期重规划间隔，并在当前路段不安全时提前失效；返航路线单独缓存；
- 目标报价只做相对代价估算，不为每次竞价运行两次 A*。

这些手段能减少重复计算，但**不保证达到固定 30 步/秒**。实际步频还受地图规模、无人机数量、服务器负载、显示转发和算法所处阶段影响。`--profile-timing` / `--profile-control-detail` 可定位瓶颈，但诊断本身也增加开销。

## 13. 当前本地测试方式与评分解释

当前 `config/competition_rescue_eval_plan.yml` 设置 Map01、10 架无人机、2 轮、无特殊区，并读取 `config/demo_bombs_map01_right_corners.json` 的 4 枚测试炸弹。YAML 顶部仍保留早期“两枚炸弹”的注释，**实际配置以 `bombs_file` 指向的 JSON 为准**。

在 MobaXterm 已配置好 X11 的会话中，可用无头模式测分并保存每步状态：

```bash
conda activate swarm
cd /data-ssd/guoyu/uav/baseline/swarm-eod
python -m swarm_rescue.launcher \
  --competition --headless --stop_at_first_crash \
  -c config/competition_rescue_eval_plan.yml
```

去掉 `--headless` 可以实时看窗口；两种方式调用相同的控制器与物理规则，但 Map01 同时有 2000 仿真步和 90 秒真实时间上限。远程窗口较慢时，90 秒内完成的仿真步数可能更少，因此实时可视化那一轮的最终轨迹/得分可能与无头轮次不同。无头运行结束后，可用输出中的 `.npz` 路径回放轨迹：

```bash
python -m swarm_rescue.launcher --replay <录制文件.npz>
```

当前蓝队评分权重为：炸弹处置 60%，健康返航 20%，步数时间分 20%，探索覆盖分权重 0%。时间分依赖结束时的**仿真步数**，不直接以墙钟秒数计算；在 2000 步上限下，1000 步以内时间分仍可能显示 100%。因此，如果 90 秒真实时间先到、只救回部分炸弹，也可能同时看到 `time score: 100%`；这**不代表已成功完成任务**。评估算法请优先看 `rescued nb`，再看健康、步数、频率和多轮稳定性。

提交前可运行蓝队单元测试与入口检查：

```bash
python -m unittest discover -s tests/solutions/blue_team -q
python scripts/check_submission.py
```

## 14. 已知边界与后续改进方向

- 当前“成本分配”是广播驱动的局部比较，不是全局最优匹配；可以继续研究任务锁定、目标所有权确认和通信失效时的去冲突。
- 栅格只在本机维护，队友不会直接获得彼此扫描过的走廊；可考虑压缩地图增量共享，但要控制消息量和融合误差。
- 前沿评分与固定比例远端侦察能改善覆盖，却无法保证所有角落都及时搜索；可用不同地图、不同炸弹布局、多随机轮次检验右下角等死角。
- 返航 A* 依赖已知自由格和设定的安全余量；狭窄通道、未知区域、携弹关节姿态会造成规划失败或实际碰撞。应结合回放检查每次失败的具体原因。
- 处置区旋转投放是针对当前抓取物理的启发式动作，不保证任何角度都快速成功；应持续统计“抓到但未处置”的比例及处置区附近耗步。
- 算法计算仍可能成为 90 秒墙钟限制下的瓶颈；优化时同时看回收率与每轮执行步数，避免只提高步频却降低策略质量。
