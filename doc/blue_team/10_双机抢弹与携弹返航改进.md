双机抢弹与携弹返航改进
====================

1. 现象与原因

最新 Map01 录制中，某枚炸弹一轮移动约 1934 像素，最终仍未到处置区。
旧策略主要倒走探索“面包屑”，只有当前点到更早轨迹点的整段路线已经
证实安全才抄近路；旧携弹安全余量 94 像素也会使很多可通行捷径
无法通过安全检查。

仿真的抓取器每机只能抓一枚炸弹，但炸弹本身可以同时被多机抓住。
前一版在纯探索时常开抓取器，容易让路过的无人机误抓队友已携带的
炸弹，两个运动命令通过关节互相牵制。

2. 双机抢弹处理

现在只有追逐可见炸弹、前往已记忆炸弹或已经携弹时才保持抓取命令；
纯探索不常开抓取器。未携弹无人机若近距离看到 `grasped=True` 的
炸弹，或收到附近队友正在携弹的消息，会临时关闭抓取器。
两机对同一目标的报价若只差少量，则按无人机编号稳定决胜，避免
观测噪声令目标所有权逐帧反转；明显更低的报价仍可获胜。

如果通信延迟使两机仍在同一时刻抓住同一枚炸弹，则用短时有效的
队友声明比较原目标位置；编号较大的无人机输出 `grasper=0` 并停止
施力，编号较小者继续运输。只在目标声明相近、且没有证据表明两机
相距很远时执行，减少误判不同炸弹的可能。没有通信或语义传感器被
禁用时，无法绝对保证冲突检测；这属于传感信息限制。

3. 携弹路线选择

抓取后先以已知处置区表面位置为目标；尚未观测到处置区时，先以
出生点为目标。控制器调用 A* 在本机传感器构建的占据栅格上寻找
已知安全路线，保留路线并逐个执行路点。每一步都会重新检查当前
路段是否安全；目标变化、路线过期或新障碍出现时再规划。

A* 暂时无法连通时，才倒走探索轨迹作为保底；轨迹中只有能通过
安全检查连接的回环才会被删除，避免反走已经形成的无意义绕圈。
携弹安全余量改为
45 像素，约覆盖机体、抓取关节和炸弹的整体半径；栅格安全检查
还有额外离散化裕量。该值比旧 94 像素更接近实际物理尺寸，仍应
通过不同地图的健康分验证。接近处置区后仍使用原来的边界对准与
持续抓持投放流程。

这是“已知地图上的安全低代价路线”，不是完整未知地图的全局
最短路线；占据栅格不完整或 GPS/激光雷达不可用时会退回轨迹。

4. 验证

新增测试覆盖：高编号重复携弹者实际输出松爪命令、已抓取炸弹使
空载机停止尝试抓取、已知地图下 A* 选择较短通道，以及 Map01
两道墙之间可找到携弹路线。蓝队测试和提交检查通过。当前环境
没有 X 显示服务，尚未在此完成整轮仿真，最终回收率和健康分
必须通过 MobaXterm 实测。

```bash
conda activate swarm
cd /data-ssd/guoyu/uav/baseline/swarm-eod
python -m swarm_rescue.launcher \
  --competition --headless --stop_at_first_crash \
  -c config/competition_rescue_eval_plan.yml
```

请保留对应轮次的 `.npz` 录制及运行日志。
