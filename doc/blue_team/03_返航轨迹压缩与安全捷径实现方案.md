当前 `_BREADCRUMB_SPACING=28`、`_BREADCRUMB_REACHED_RADIUS=36`、
`_MAX_BREADCRUMBS=600`。未携弹时 `_record_breadcrumb()` 按 GPS
距离添加点；抓取边沿时强制添加最后一点并复制到
`_return_waypoints`；携弹时 `_next_return_waypoint()` 从尾部弹出
已经抵近的点；一旦语义传感器直接发现回收区，
`_control_carry()` 改用父类的精确投放逻辑。

这个策略比直接穿墙可靠，但有四个具体问题：

1. GPS 跳点、相关噪声、回环与走廊来回试探被原样保存。
2. `del _breadcrumbs[1]` 超过 600 点时可能删掉关键入口，
   后续两点之间变成长跳，逆序路线不再连续。
3. 抓取后的炸弹扩大占用空间；“空载走过”不等于“载弹能逆走”。
4. 路线没有版本、地图安全证书、堵塞回滚和重规划状态。

更关键的是尺寸：`DroneAbstract.__init__` 虽给父层传入
`radius=10`，但 `Agent` 继承的 `Entity` 会接收并忽略这项额外参数。
实际 `DroneBase` 没有再传半径，它使用 24×24 精灵的 hull 作为
Pymunk 碰撞体。机身外接半径初版按不大于 `sqrt(12^2+12^2)`，
即约 17 像素做保守估计，不能把 10 像素当成可通行证明。
炸弹 `Bomb(radius=12)` 则确实经 `EmbodiedEntity` 缩放到外接
半径 12。精确物理轮廓可在开发环境离线校准，但控制器内不能
读取真值形状或实体位姿来替代测量。

2. 目标与非目标

目标：

1. 保留一条按时间可追溯、坐标 frame 一致的原始出航轨迹。
2. 清洗假跳点和冗余点，在安全验证通过时缩短载弹返航距离。
3. 任何捷径都要经过已知自由栅格的载弹包络检查；未知区域
   不当成可穿越空白。
4. 地图过期、定位失效、动态阻挡时明确退回原轨迹、请求 A*
   或暂停扫描，不偷偷执行未经验证的直线。
5. 给协调器输出路线、进度、下一个 `NavigationGoal` 和重规划请求。
6. 保留既有 Lidar 安全层与回收区附近的精确投放动作。

非目标：不自己实现全图建图、定位滤波、炸弹竞价、机械爪控制、
电机命令或评分器；不使用地图 JSON/PNG 真值、`true_*` API、
炸弹真实位置或 Pymunk 内部关节状态作为策略输入；不宣称靠地图
静态检查可以避开未来临时移动的其他无人机。

`blue_team/contracts.py`（共享，需四模块共同确认）：

```python
class ReturnPathManager:
    def __init__(self, drone_id: int, config: ReturnPathConfig) -> None: ...

    def begin_carry(self, data: ReturnInput,
                    checker: Optional[SegmentSafetyChecker]) -> ReturnRoute: ...
    def update(self, data: ReturnInput,
               checker: Optional[SegmentSafetyChecker]) -> ReturnOutput: ...
    def accept_replan(self, plan: PathPlan,
```

记录器只管可信轨迹采样和截断标记；管理器只管返航路由、验证、
进度与状态，不触发机械爪、不改占据图、不自行调用 `control()`。
`begin_carry()` 只在真实抓取上升沿调用一次。

`blue_team/occupancy_grid.py`（地图负责人，需增量接口）：

```python
class SegmentSafetyChecker(Protocol):
    def check_segment(self, start: WorldPoint, end: WorldPoint,
                      clearance: float, map_revision: int,
                      frame_id: str) -> SegmentCheck: ...

    def segment_is_safe(self, start: WorldPoint, end: WorldPoint,
                        clearance: float, map_revision: int) -> bool: ...
```

输入为两世界点、载弹清障半径、地图版本与 frame；输出是
`SegmentCheck`。具体膨胀栅格、角落穿越检查由地图模块拥有；
返航模块不得绕过 checker 自己去读栅格内部数组。

`blue_team/path_planner.py`（A* 负责人，需增量接口）：

```python
class ReplanProvider(Protocol):
    def plan(self, start: WorldPoint, goal: WorldPoint,
             carrying: bool, clearance: float,
             max_expansions: int, frame_id: str) -> PathPlan: ...
```

返回 `PathPlan`，其 `waypoints` 仍需返航模块逐段用相同载弹
清障半径验证；A* 输出不能自动等于安全证明。02 方案的成本查询
接口应复用该规划器的路线成本结果或适配器，不产生第二套单位。
只有协调器调用 `plan()`；返航模块只发 `ReplanRequest`，
并在 `accept_replan()` 中校验返回路线和生成新版本。

`blue_team/coordinator.py`（共享集成）：

```python

    def choose_motion_goal(self, task_output, return_output,
```

5. 公共数据契约

公开类型用 `typing.Tuple`、`Optional` 等 Python 3.8 风格。
现有控制器用 `list[...]`，若比赛解释器真为 3.8，还须单独做
完整兼容检查；本设计不擅自改动其他人的模块。

```python
from dataclasses import dataclass
from typing import Optional, Tuple

WorldPoint = Tuple[float, float]

@dataclass(frozen=True)
class PoseEstimate:
    position: Optional[WorldPoint]
    heading: Optional[float]
    position_variance: float       # px^2
    heading_variance: float        # rad^2
    source: str
    frame_id: str
    step: int
    valid: bool

@dataclass(frozen=True)
class NavigationGoal:
    goal_id: str
    kind: str                     # BOMB_RETURN / DISPOSAL_APPROACH
    position: WorldPoint
    tolerance: float              # px
    priority: float               # [0,1]；返航取 1
    created_step: int

@dataclass(frozen=True)
class ReturnRoute:
    route_id: str
    status: str
    waypoints: Tuple[WorldPoint, ...]
    next_index: int
    raw_point_count: int
    compressed_point_count: int
    estimated_length: float       # px
    safety_margin: float          # px，建路时最小许可 clearance
    map_revision: int             # 无地图为 -1
    created_step: int
    reason: str

@dataclass(frozen=True)
class RouteProgress:
    route_id: str
    status: str
    active_waypoint: Optional[WorldPoint]
    next_index: int
    remaining_distance: float     # px；未知时为 inf，仅本地使用
    deviation: float              # px；未知时为 inf，仅本地使用
    replan_required: bool
    step: int
    reason: str

@dataclass(frozen=True)
class ReplanRequest:
    route_id: str
    start: WorldPoint
    goal: WorldPoint
    carrying: bool
    clearance: float              # px
    frame_id: str
    map_revision: int
    created_step: int
    max_expansions: int
    reason: str

@dataclass(frozen=True)
class SegmentCheck:
    status: str                   # SAFE / BLOCKED / UNKNOWN / STALE
    min_clearance: float          # px；无法计算时为 -1
    checked_cells: int
    map_revision: int
    reason: str

@dataclass(frozen=True)
class ReturnInput:
    step: int
    steps_left: int
    pose: PoseEstimate
    carrying: bool
    just_grabbed: bool
    just_released: bool
    verified_clear: bool
    disposal_seen: Optional[WorldPoint]
    disposal_memory: Optional[WorldPoint]
    disposal_frame_id: Optional[str]
    lidar_front_min: Optional[float]
    lidar_left_min: Optional[float]
    lidar_right_min: Optional[float]
    lidar_step: int
    map_revision: int
    map_frame_id: Optional[str]
    map_staleness_steps: int
    drone_id: int
    carried_track_id: Optional[str]

@dataclass(frozen=True)
class ReturnOutput:
    route: ReturnRoute
    progress: RouteProgress
    goal: Optional[NavigationGoal]
    replan_request: Optional[ReplanRequest]
    raw_length: float             # px
    compressed_length: float      # px
    compression_ratio: float      # raw / compressed，压缩不可用为 1
    fallback_reason: str
```

`ReturnRoute.waypoints` 固定为“从炸弹处往出生/回收准备点走”的顺序。
第 0 个是抓取后的第一个待到达点，不再包含当前位置；
`next_index=0` 时跟踪 `waypoints[0]`，绝不可再次反转。
`raw_point_count` 和 `compressed_point_count` 均计待到达点数，
不计当前抓取点；`estimated_length` 则计当前抓取点到首点的首段。
`waypoints` 是不可变 tuple，调用方不能 pop 或就地改写。
路线变化创建新的 `route_id` 版本后缀或 route revision；
历史 `ReturnRoute` 对象仍可用于日志，但不能继续导航。
未抓取时 `ReturnOutput.route` 用空 `waypoints`、
`status="RECORDING"`、`map_revision=-1` 的哨兵对象，
避免调用方把 `None` 当作已构建路线；其 `goal=None`。

`ReturnRoute.status` 完整集合及含义：

```text
RECORDING      正在记录出航轨迹，尚无返航路线
READY          已生成可执行路线；待下一控制周期开始跟踪
FOLLOWING      正在跟踪经过当前安全验证的路线
DEGRADED_RAW   捷径不合格，谨慎逆走原始轨迹并逐段重检
BLOCKED        当前段被动态障碍暂时挡住；先停/绕，不改静态地图
REPLAN_PENDING 原路线无法继续，等待 A* 请求或结果
COMPLETED      到达回收准备区/转交精确投放，或任务已确认清除
INVALID        缺少必要位置、轨迹断裂且无安全回退
```

`RouteProgress.status` 完整集合：

```text
RECORDING / READY / FOLLOWING / DEGRADED_RAW / BLOCKED
REPLAN_PENDING / COMPLETED / INVALID
```

两类对象共用有限状态，避免协调器隐式翻译。
`COMPLETED` 若只是移交精确投放，不等于炸弹已经销毁；
任务模块仍需等正奖励确认清除，不能靠路线完成发墓碑。
`INVALID` 不表示可以放开 grasper，而是要求控制器安全停下
或执行局部避障，并继续寻找重规划可能性。

`SegmentCheck` 是检查器唯一可信反馈。只有 `SAFE` 可用于
几何捷径；`UNKNOWN`、`STALE`、`BLOCKED` 都不能被转换成 True。
如果共享地图只提供题目建议的 `segment_is_safe()->bool`，
可用它作为兼容外壳；实际返航内部仍应要三态以上原因。

6. 原始轨迹记录

6.1 样本结构和采样时机

`BreadcrumbRecorder` 内部保存 `TrailSample`：

```python
@dataclass(frozen=True)
class TrailSample:
    position: WorldPoint
    position_variance: float
    heading: Optional[float]
    step: int
    frame_id: str
    keypoint: bool
    source: str
```

每步定位输出后调用 `update()`，但不是每步都存。
若与上个有效点相距至少 28 px，或超过 15 步，或
航向累积变化超过 35 度且位置变化至少 8 px，则记录。
强制 keypoint 可用于回合起点、走廊入口、A* 转弯、脱困开始/结束、
重新定位锚点和抓取瞬间。停在原地转身时不重复写几十个相同点，
只更新最近点的 heading 与时间；但要记录转弯事件标志。

采样距离随不确定性缩小：

```text
spacing = clamp(28 - 0.35 * sqrt(pos_var), 12, 28) px
```

方差大时更密地保留轨迹结构，但 `pos_var > 400 px^2`
时不应因为密采样就把不可信位置当可靠路径：暂停世界轨迹记录，
由定位模块继续用里程计/指南针融合；恢复后加入重定位锚点。
里程计单步行程噪声约 0.2 px，alpha 约 8 度，theta 约 1 度；
可以使用定位模块输出的 `ODOM_COMPASS_FUSED` 世界位姿，
不得自己把 odometer 原始相对增量误当世界坐标。

6.2 GPS 跳点、相关噪声和分段

GPS 自回归噪声初始尺度约 5 px，有时间相关性，
不是连续两帧均值后就可认为误差归零。以下任一条件触发隔离：

- 坐标非有限、frame 与当前段不同、`valid=False`；
- 相对上一有效点的位移大于可运动学上界，例如
  `max(40, 3 * measured_speed * delta_steps + 20)` 像素；
- 位移与同期里程计累计行程严重矛盾，且连续两帧不能复现；
- `position_variance` 明显突增到阈值以上。

异常样本先入候选缓冲，连续 2 帧相互一致且定位模块已重锚时
才开始新段；一帧孤立跳点直接丢弃。若 `frame_id` 发生变化，
结束旧段并显式记断点，绝不连接两个 frame 的坐标。
同一世界 frame 内 GPS 短断时，若定位模块仍给有效融合位姿，
继续记录并保留较大方差；若仅剩 `local:dX:eY` 坐标，
不与世界点混接。恢复后能否把局部段转换回 world，
由定位模块提供经过验证的刚体变换；否则此段返航不可复用。

6.3 600 点上限与抓取点

绝不简单执行 `del samples[1]`；这会在旧点和新点之间制造
未经验证的长线段。实现“两级存储”：前 80 个关键锚点、
最近最多 520 个细点，共计不超过 600。需要回收内存时，
仅能把一个连续的旧轨迹块经几何和地图安全检查压成保留端点；
安全检查不过就标 `overflow_gap=True`，保留出生锚和最近轨迹，
明确记录断裂区间，禁止把断裂两端直接连接。

首版若地图组件尚未接入：可以继续保留最近 599 点与出生锚，
但一旦上限触发就把路线质量标为 `INCOMPLETE` 内部标志；
抓弹后直接请求 A* 或进入近距保守扫描，不能谎称原始轨迹完整。
抓取上升沿必须用当步有效位姿插入最后一个点，哪怕距离上一点
不足采样间距；若当前 world 位姿不可用，记录 `PICKUP_UNLOCATED`，
不根据旧点假定炸弹所在位置。

投放成功并确认 `verified_clear=True` 后，以当前位置为新起点
重置 recorder。若只是松爪而没有奖励，任务模块负责发 DROP，
返航模块销毁当前携弹路线、保留可用出航轨迹诊断数据，
新任务从当前可用位置重新开始记录，不标记“已完成清除”。

7. 清洗和压缩流水线

严格分开“几何候选”和“允许执行的安全路线”：

```text
原始 TrailSample
  -> 有效性与 frame 清洗
  -> 重复点与 GPS 孤点清理
  -> 保留首尾、入口、转角、重定位点
  -> 小回环候选检测
  -> 已知自由空间下的回环删除
  -> 局部几何简化候选
  -> 安全线段检查与最远可见点选择
  -> 路线版本、证书和原始回退链
```

7.1 输入清洗

删除非有限坐标和同帧 3 px 内重复点；两个样本间如果缺失的
时间太长、运动学不可能或 frame 不同，插入内部 `GAP` 标记。
清洗过程绝不跨 `GAP` 连线。首点、抓取点、每次强制 keypoint、
转角超过 35 度点和窄走廊入口不得被径向抽稀直接删除。
被拒绝的点记在调试计数中，不纳入路线长度。

7.2 选择的几何方法

- 径向距离抽稀：在线 O(1) 摊销；与时间、转角规则一起用于记录。
- 滑动三点共线检查：窗口 3 到 5 点，线段最大横向偏差
  不超过 6 px 时生成可删除候选；真正删除仍要地图验证。
- 小回环检测：最近 120 点中非相邻点在 18 px 内，
  且中间已走长度至少 60 px，则视为回环候选。删除前检查
  返回连接端之间的载弹安全性；否则保留原路径。
- Ramer-Douglas-Peucker：不是首版最终决策方法。
  RDP 只保证点线距离小，可能从 U 形墙一端直接穿墙；
  若以后使用，必须逐条通过同一个安全 checker。

首版推荐“局部共线候选 + 窗口化最远安全可见点”。
取抓取点作为当前起点，按逆序原始点看未来最多 12 个节点，
从最远候选开始检查；第一个 `SAFE` 的点作为下个 waypoint；
若都不安全，保留相邻原始点，但它也只能在局部实时检查后执行。
每次最多处理一个窗口并缓存结果，不在抓取的同一步把 600 点
两两组合检查。剩余窗口可在后续控制周期滚动压缩。

伪代码：

```text
raw = clean_and_reverse_outbound(samples)
if has_gap(raw):
    mark_incomplete(); request_replan_if_possible()
else:
    i = pickup_index
    while i < raw.last and budget_allows():
        far = min(i + 12, raw.last)
        chosen = i + 1
        for j in range(far, i + 1, -1):
            check = safety.check_segment(raw[i], raw[j], clearance,
                                         revision, frame)
            if check.status == SAFE and turn_at_j_is_feasible(j):
                chosen = j
                break
        append_waypoint(raw[chosen])
        i = chosen
    keep_unprocessed_tail_as_degraded_raw()
```

复杂度：清洗 O(n)；窗口大小固定 12，最多 `O(12n)` 次
候选检查，但受总查询预算约束。提升版可在不超过 80 个
关键点上建有向无环图：每条合法安全边有长度和风险成本，
再做 DAG 最短路，最坏 O(k^2) 条边；只在地图稳定、
计算预算允许且每条候选边均验证时启用。贪心先降低工程风险。

8. 安全线段检查

8.1 地图接口返回什么

`SegmentSafetyChecker.check_segment()` 只使用无人机维护的
三态占据栅格及其 `frame_id/revision/last_update_step`，
不能调用官方地图真值、PNG 像素墙位或仿真器内部 shape。
地图负责人应预先计算已知静态障碍的距离场或膨胀占据图；
返回 `SegmentCheck(status, min_clearance, checked_cells,
map_revision, reason)`。`SAFE` 仅表示这张有时效的局部地图
中，该线段所需包络经过的所有格均为已知自由且有足够间距；
未来动态障碍仍靠每步 Lidar 检测。

检查流程：

```text
if frame 不同 or revision 不同: STALE
if start/end 越界 or 地图缺关键局部区域: UNKNOWN
用 supercover 遍历线段穿过的全部栅格，包括贴边角格
对每个访问格及膨胀半径内邻格：
    UNKNOWN -> UNKNOWN
    OCCUPIED -> BLOCKED
    known_free 但距离场 < clearance -> BLOCKED
检查端点圆盘和转角圆盘；不足 clearance -> BLOCKED
全部通过 -> SAFE(min_clearance, checked_cells, revision)
```

栅格坐标的角落穿越必须检查被线段同时触及的两个相邻格，
不能只检查 Bresenham 主对角格。未知栅格会使捷径失败；
已见过的空间但长时间无更新时，如果地图负责人将其标未知，
也不可被本模块擅自视为自由。地图版本发生变化只使相关
证书失效；不必全量重算 600 点，而是先重检当前段与下一段，
空闲预算再延伸。地图负责把动态无人机从静态墙层剥离，
短暂遮挡只交给 Lidar 阻挡状态机，不永久写墙。

8.2 超出 Lidar 量程

300 px 是 Lidar 单次最大量程，不是“超过 300 就一定不可规划”。
若长线段全程都有近期已知自由地图覆盖、膨胀证书有效，
可以作为远期路线候选；执行时每一步仍要对当前局部
前方约 80 至 120 px 做实时 Lidar 检查。
没有地图证书时，长度超过 `min(240, 300 - margin)` 的
新捷径一律不启用；长度较短也不能只看一条正前射线就证明
载弹包络安全，必须用覆盖走廊角度扇区的多条射线与侧边
间距，并考虑测距噪声。首版最安全的规则是：
“Lidar 单独不生成全新跨未知区捷径”，只为原路径和
已获地图证书的路线提供实时否决与减速信号。

8.3 条件性安全证明

给定两个连续点 A、B，只有以下前提同时成立才可称
“地图意义上载弹安全”：

1. 两点位于同一可靠 world frame，位姿标准差不超预算。
2. 所有被线段与所需半径扫过的栅格都是已知自由；
   障碍距离场最小值至少为计算出的 `clearance`。
3. 栅格覆盖采用 supercover 和端点圆盘，不漏斜对角贴角格。
4. 炸弹中心相对无人机中心距离确实不超过采用的
   `L_attach_max`；若无法建立此界，则禁止自动捷径。
5. 转弯点可停下并原地转向，或已检查转角圆盘。
6. 计划沿线执行期间持续用最新地图和 Lidar 复核。

在这些前提下，以无人机中心线段为轴扩张 `clearance`
的圆盘走廊，包含模型里的载弹组合外形；由于整个走廊
落在已知自由区域，静态墙碰撞在模型和不确定度预算内
不会发生。这里不是对实际动态物理世界的绝对证明：
若关节超出假设、地图漏墙、误差超过预算或其他无人机
突然进入走廊，仍可能碰撞，运行时必须立即停/绕。

9. 携弹安全间距

9.1 源码几何与抓取关系

机身精灵约 24×24 像素，碰撞形状为 hull；保守外接半径
`r_drone=17 px`。炸弹的外接半径 `r_bomb=12 px`。
`Grasper` 是比机身外接半径多约 5 px 的交互形状；
抓取时给机身和炸弹加 `PivotJoint`，枢轴初始点是
`0.3 * drone_center + 0.7 * bomb_center`。这不是定长拉杆，
但局部锚点在两个刚体上固定；在理想刚性约束下，
两中心距离上界不大于抓取瞬间的距离。抓取瞬间碰撞
给出粗略上界 `17 + 5 + 12 = 34 px`。再给求解误差和
离散时间留 6 px，设建议 `L_attach_max=40 px`。
这只是基于源码的保守工程界，必须通过离线物理仿真
测试校准；若观测到超过 40，就上调，不能改小继续声称安全。
比赛控制中不能读取炸弹真实坐标来动态缩小此值。

9.2 包络公式及数值

直接相加 `r_drone + r_bomb` 并不能描述悬在机身外的炸弹。
载弹组合相对无人机中心的包络取：

```text
r_payload = max(r_drone, L_attach_max + r_bomb)
pose_margin = clamp(3 * sqrt(position_variance), 8, 30) px
grid_margin = grid_resolution * sqrt(2) / 2
lidar_margin = 3 * 2.5 = 7.5 px
clearance = r_payload + pose_margin + grid_margin
          + lidar_margin + fixed_margin
```

首版：`r_drone=17`、`L_attach_max=40`、`r_bomb=12`，
因此 `r_payload=52 px`；`fixed_margin=5 px`；
栅格分辨率建议 20 px 时 `grid_margin=14.2 px`；
位姿方差 25 px^2 时 `pose_margin=15 px`；
得到 `clearance≈93.7 px`。地图 checker 用 94 px 向上取整。
若地图距离场精确按单元边界而非中心计算，`grid_margin`
可在地图负责人证明后减小；未经验证不能提前减小。

各项范围及责任：

- `r_drone`：17 px 默认；离线核验物理 hull 后只允许上调或
  经证据下调，控制器不读物理真值。
- `r_bomb`：12 px，源码可确认；比赛规则改动时重新核验。
- `L_attach_max`：40 px 建议，至少 34 px 加求解余量；
  若无法给出可靠上界则捷径 feature flag 关闭。
- `pose_margin`：8 到 30 px；方差非有限或高于 400 px^2
  直接禁止新捷径，而不是把不确定性钳到 30 后仍运行。
- `grid_margin`：20 px 栅格约 14.2 px，随分辨率变；
  超过 40 px 先考虑建图分辨率过粗，不盲目取捷径。
- `lidar_margin`：7.5 px；Lidar 无效时地图静态证书仍可
  作为远期路径，但当前移动应减速/暂停，不能取消安全层。
- `fixed_margin`：5 px，至少 5；没有实测不得调到 0。

由于默认包络很保守，狭窄走廊可能无法认证任何捷径；
这时保留逐段原路线并用实时 Lidar 检查，或者请求携弹 A*。
原路线也可能空载能通过、载弹不能通过，所以它不是无条件
安全兜底。真正的兜底是“限制速度、逐段查障、遇险停止并重规划”，
不是强行沿原路撞墙。

转角风险单独处理：若路线在某点转向超过 45 度，先在
该点减速至 0、转向，再沿下一段出发，并验证以该点为中心
半径 `clearance` 的圆盘；未满足时在相邻安全开阔格插入转向点。
这样使用圆盘包络覆盖炸弹转弯扫掠，而非只检查两条中心线。

10. 路线跟踪和失效恢复

10.1 waypoint、偏差、进展

首个目标为 `route.waypoints[route.next_index]`。
到达条件为 `distance(pose, goal) <= 18 px` 连续 2 帧，
且位姿有效；GPS 方差增大时容差可扩到 24 px，但不得
超过目标点所在安全圆盘半径，避免跨墙误判。
每次到达后推进 `next_index`；不修改原 tuple。

横向偏差是当前位置到当前路线段的线段距离，投影参数
截断到 `[0,1]`，不能用无限长直线距离。
`deviation > max(35 px, clearance/2)` 连续 5 步，
或实际距离下个 waypoint 在 30 步内减少不足 10 px，
进入 `BLOCKED`/`REPLAN_PENDING`。转身和投放阶段
不计入“前进不足”计时，防止误判。

`RouteProgress.remaining_distance` 等于当前位置到当前 waypoint
的距离，加剩余各段预计算长度；无可靠 pose 时用 `inf`。
给协调器的 `NavigationGoal.tolerance` 初值 18 px，
优先级 1。协调器必须在不改变 `waypoints` 的前提下
选择动作，并可把 Lidar 脱困结果回报给路线管理器。

10.2 各类失效处理

- 新地图版本：立即暂停使用受影响的当前捷径证书，
  以新 revision 检查当前段和下一段；安全则继续并更新证书，
  不安全就先尝试回退到原始链。
- 地图把当前 waypoint 或转角圆盘判为占据：当前捷径无效；
  对同一 frame 的原始路线从最近可达锚点接续，再不行请求 A*。
- Lidar 近距有人/物短暂挡路：连续 2 步阻挡进入 `BLOCKED`，
  停止推进该 waypoint，保持 grasper；允许现有 Lidar 脱困
  在安全距离内侧移/旋转。连续 8 步阻挡才考虑绕行，
  连续 25 步仍堵再请求 A*；不能把临时机体写成静态墙。
- 地图证书缺失但原始链连续：进入 `DEGRADED_RAW`，
  只走下一条近距原始边；用 Lidar 检查，当边也不安全就停。
- 原始链断裂、当前 pose frame 不匹配、连续 5 步无可靠位置：
  `REPLAN_PENDING` 或 `INVALID`，请求可用定位/A*；
  绝不朝回收区记忆点直接穿墙。
- A* 返回 `READY`：逐段用相同 `clearance` 和当前地图版本
  验证，再构造新路线；`NO_PATH`：等待地图更新/局部扫描；
  `BUDGET_EXCEEDED`：下步续算或保持原安全边；
  `STALE_MAP`：先更新地图版本重试。

10.3 何时移交精确投放

若语义本步直接看到回收区，且相对距离小于约 80 px，
本机与回收区之间的局部 Lidar 扇区未被判阻挡，并且
原生 measured GPS/compass 可用，就返回 `DISPOSAL_APPROACH`
目标并让控制器调用现有父类近距精确投放分支；
直接看见但仍隔着狭窄墙角
时不跳过返航安全检查。若本机已足够靠近回收区但 GPS
不可靠，不能直接调用父类 `_control_carry()` 期待其完成投放：
其 `_move_toward()` 同样依赖 measured GPS/compass。
只有实现了经过测试的 `_move_toward_estimate()`，并有
有效 world 位姿及航向，才能继续安全接近；若只有机体系
语义、没有可用定位，首版应停/扫描等待重定位，
不凭单条射线盲推入回收区。

路线到达出生/准备点但仍未看到回收区时，不宣布任务成功，
输出 `COMPLETED(reason="at_staging_wait_disposal")` 仅代表
路线结束；协调器继续围绕准备点谨慎搜索回收区。
真正投放过程中 `grasper=1` 由现有 `_control_carry()`
负责维持，直到精确投放逻辑判定释放；返航模块始终不设置
`grasper` 字段、不生成 `CommandsDict`。

11. 输入契约

`ReturnPathManager` 每控制步收到一个 `ReturnInput`，
每项含义、来源、缺失处理如下：

- `step/steps_left: int`：协调器读取 `elapsed_timestep` 和
  `MiscData.max_timestep_limit`；未知剩余步传 -1，
  不用墙钟做租约或路线进度判据。
- `pose: PoseEstimate`：定位模块，世界像素、弧度、方差和 frame；
  `step` 超过 2 步未更新或 `valid=False` 时禁新捷径。
- `carrying/just_grabbed/just_released: bool`：控制器依据
  `bool(grasped_bombs())` 的前后边沿，不能由消息推断本机携弹。
- `verified_clear: bool`：由任务模块按上一物理步 `reward>0`
  与携弹边沿确认；无奖励的松爪只能取消路线，不能记成功。
- `disposal_seen: Optional[WorldPoint]`：本步语义射线换算的
  回收区世界点；通常只在 200 px 内可用，缺失传 None。
- `disposal_memory/disposal_frame_id`：控制器或定位模块的
  最近可信回收区估计；超过 120 步未刷新则只能用于
  大致准备区，不用于无检查直达。
- `lidar_front/left/right_min`：控制器按 181 射线计算
  的有限最小距离，单位 px；无 Lidar 传 None；
  `lidar_step` 超过 1 步则视为过期。
- `map_revision/map_frame_id/map_staleness_steps`：地图模块；
  地图不可用传 -1/None/大数，不可把未知格判自由。
- `drone_id/carried_track_id`：控制器和任务分配模块；
  track ID 缺失只影响关联日志，不阻止救援返航。

其他只读服务：

```python
checker: Optional[SegmentSafetyChecker]
planner: Optional[ReplanProvider]  # 仅协调器持有
```

`checker` 由 `occupancy_grid.py` 提供，`planner` 由
`path_planner.py` 提供。路线管理器只输出重规划请求，
由协调器调用 planner 并把结果交回路线管理器；管理器不持有
底层栅格数组或地图真值。机身半径、炸弹半径、抓取上界、
安全冗余由 `ReturnPathConfig` 提供，源码值经离线测试确认后
所有无人机用同一参数。02 目标分配模块需要返航预测长度时，
可向路径服务询价；本模块的实际回程长度只在抓取后形成，
不能在拍卖时假装已有完整返航路线。
`map_staleness_steps > 40` 时管理器拒绝新增捷径，
即使 checker 暂时还持有旧 revision；当前局部段须重新检查。

12. 输出契约

`begin_carry()` 返回一次 `ReturnRoute`；`update()` 每步返回
`ReturnOutput`，包含不可变路线、进度、导航目标和可选重规划请求。
`ReturnRoute` 给协调器及日志；`RouteProgress` 给协调器、
健康监控与日志；`NavigationGoal` 给现有运动层；
`ReplanRequest` 给 A* 负责人；长度、点数与回退理由给调试/评测。

实际路线对象：

```python
ReturnRoute(
    route_id="return:d6:t901:v1",
    status="READY",
    waypoints=((430.0, 250.0), (260.0, 150.0),
               (-90.0, -120.0)),
    next_index=0,
    raw_point_count=73,
    compressed_point_count=3,
    estimated_length=612.4,
    safety_margin=94.0,
    map_revision=48,
    created_step=901,
    reason="validated_window_shortcuts",
)
```

这个示例是假设所有三段都通过 version=48 的安全检查，
并非由现有地图真实生成；数值只演示字段格式。
对应进度与目标：

```python
RouteProgress(
    route_id="return:d6:t901:v1",
    status="FOLLOWING",
    active_waypoint=(430.0, 250.0),
    next_index=0,
    remaining_distance=612.4,
    deviation=4.2,
    replan_required=False,
    step=902,
    reason="current_segment_valid",
)

NavigationGoal(
    goal_id="return:d6:t901:v1:0",
    kind="BOMB_RETURN",
    position=(430.0, 250.0),
    tolerance=18.0,
    priority=1.0,
    created_step=902,
)
```

需要重规划时的对象：

```python
ReplanRequest(
    route_id="return:d6:t901:v1",
    start=(406.0, 268.0),
    goal=(-90.0, -120.0),
    carrying=True,
    clearance=94.0,
    frame_id="world",
    map_revision=49,
    created_step=918,
    max_expansions=1500,
    reason="current_shortcut_blocked_after_map_update",
)
```

协调器不得修改 `waypoints`、`next_index` 或 `status`；
若导航失败，只能把失败事件回报给 `ReturnPathManager.update()`，
由管理器发布新版本对象。

13. 单步调用时序

运行顺序必须使抓取事件和路线创建在同一个 `control()` 中生效：

```text
1. 控制器读测量 GPS/指南针/里程计/语义/Lidar、
   grasped_bombs、reward 和逻辑步数
2. 定位模块给 PoseEstimate，地图模块更新 revision
3. 目标分配模块处理抓取/奖励硬事件，给出 carried_track_id
4. 未携弹：ReturnPathManager.record_outbound(pose, step)
5. 本步刚抓取：force 写入抓取点；begin_carry() 固化原始链
6. 携弹：update() 检查当前证书、Lidar 阻挡、进度和回收区
7. 有 ReplanRequest：协调器按预算询问 A*；返回后连同 checker
   调用 accept_replan()，由返航模块检查每段安全
8. 有 DISPOSAL_APPROACH：调用现有精确投放逻辑
9. 否则有 BOMB_RETURN：运动层 _move_toward() 并保留 Lidar 安全层
10. 再否则停/局部扫描/脱困；携弹期间保持 grasper=1
11. 松爪且有确认奖励：返航路线结束并重置 recorder
12. 松爪无奖励：销毁携弹路线、发 DROP，重新定位掉落炸弹
```

现有仿真循环在 `control()` 前收集待发广播、随后执行物理步。
此模块不需要单独广播路线；如果协调器决定把返航状态放入
统一 v2 消息，必须使用上一控制周期缓存，不能假定本步
调用 `update()` 的结果会在本步被队友收到。

14. 与现有代码的迁移步骤

逐项替换且保留可回退开关：

- `_breadcrumbs`：迁到 `BreadcrumbRecorder` 的 `TrailSample`
  列表；旧 list 仅在 `RETURN_PATH_MODE="legacy"` 时使用。
- `_return_waypoints`：迁到不可变 `ReturnRoute.waypoints` 与
  `next_index`，禁止通过 `pop()` 改动路线本体。
- `_record_breadcrumb()`：控制器只构造 `PoseEstimate` 并调用
  `record_outbound()`；采样、跳点、关键点由 recorder 管。
- `_next_return_waypoint()`：改读 `ReturnOutput.goal`；
  waypoint 到达、偏离和卡住由 manager 返回 `RouteProgress`。
- `_control_carry()`：保留现有精确投放与 Lidar 脱困原语；
  非近距阶段只跟踪经 manager 给出的 `BOMB_RETURN` 目标。
- `_mark_current_target_cleared()`：与 02 方案一致，只在
  `reward>0` 且前一周期确实携弹时标清除；无奖励掉落不能
  触发返航成功或删除轨迹证据。

渐进迁移与单独验收：

1. `legacy_adapter`：把现有 GPS 点和逆序访问封装进 manager，
   不做压缩；同一布局回放输出应与旧版 next-waypoint 一致。
2. 加清洗：只去假点、重复点和断帧连接；回放须不增加
   错误长跳，返航成功率不下降。
3. 加地图安全捷径：只在 checker 返回 `SAFE` 时跳点；
   U 墙和未知格测试必须阻止穿越。
4. 加失效与 A*：地图更新、临时无人机阻挡和 GPS 失效
   都应进入明确状态，而非重复撞墙。
5. `RETURN_PATH_MODE` 可选 `legacy`、`clean_raw`、
   `safe_shortcut`；任何阶段异常可切回 `clean_raw`，
   但这个模式仍需逐段 Lidar 保护，不能宣称绝对安全。

注意：02 方案的 `CARRYING -> RELEASED/LOST` 事件应作为
返航模块的 `verified_clear/just_released` 输入，
不能让返航模块再次用坐标推断是否清除。

16. 性能和复杂度

每步轨迹记录 O(1) 摊销，GPS 跳点与转角比较只看最近少量样本。
原始轨迹最多 600 点；抓取瞬间做一次 O(n) 清洗和反转，
不做 600×600 全组合查询。抓取当步最多 24 次地图段检查，
以后每控制步最多 8 次新捷径检查、4 次原路线检查。
因此短时间内尚未压完的尾段标为 `DEGRADED_RAW`，
只让当前已验证局部段进入运动层。
600 点情形的抓取瞬间目标耗时设为 8 ms：开始检查前记录
`time.perf_counter()`，超过预算立即停止压缩，返回已验证前缀
和原始尾段，后续分步继续。8 ms 是需要基准测试的目标，
不是 Python 或操作系统保证的硬实时上界；单次栅格查询仍必须
有访问格数上限，防止一个长线段拖慢整步控制。

假设每段检查触及不超过 100 个栅格，抓取当步约 2400 格
访问；实际长线段和大 clearance 会更多，需加单次
`checked_cells <= 3000` 上限，超过返回 `UNKNOWN`。
固定 12 点窗口把几何候选数控制在最多约 7200，
但本回合只按预算逐步处理，不一次性全部检查。
升级版关键点 DAG 如有 80 点，约 3160 对候选，
只允许离线或低频重规划时分批运行，不能每步重建。

安全查询缓存键必须含：`(frame_id, map_revision, index_i,
index_j, quantized_clearance, route_version)`。位姿方差增大或
载弹半径参数变化时不同 clearance 不共用缓存；
地图 revision 改变立即失效，不能继续拿旧 SAFE 当证书。
缓存上限 256 项，采用 LRU；原始样本上限 600，
公开路线最多 600 个世界点、常态预期远少于此。
以两个 64 位坐标、方差、步数与若干标志估计，
每机轨迹与缓存通常在数百 KB 量级；真实 Python 对象
开销必须用目标解释器测量，不在这里作硬保证。

17. 失败模式和退化策略

- 地图不可用：不创建几何捷径；保留完整原始链，
  按下一条近距边和当前 Lidar 谨慎行进。若也不能确认安全，停。
- 地图更新/新墙：旧证书立刻过期；先核对当前边，
  再尝试原链，最后请求 A*；不直接跳到回收区。
- GPS 暂断、里程计融合仍给可靠 world frame：继续当前路线，
  但须经控制器 `_move_toward_estimate()` 适配器执行，
  不添加高风险捷径；方差上升时加大安全间距。
- GPS 失效且仅有局部 frame：暂停世界路线，继续持弹，
  原地安全旋转寻找回收区语义或等待重定位。
- GPS 单点跳变：隔离点，不让它造成跳跃捷径。
- 轨迹内存满：只删除已验证可替代的旧段；不能验证时显式
  `overflow_gap`，请求规划，禁止跨 gap 连线。
- 其他无人机挡路：先停与侧向避让，连续阻挡再重规划；
  不能把动态实体永久写进静态墙层。
- 携弹外形超过模型上界：立即关闭捷径，增加安全参数，
  必要时走保守原链或停；不能继续沿被错误认证的窄段前进。
- 无可行安全回路：`INVALID` 或 `REPLAN_PENDING`，
  继续保护 grasper、局部扫描，等待地图/定位改善；
  不因时间压力强制穿墙。
- 只有出生点，没有可信回收区：先到出航起点附近，
  再用语义寻找回收区；不能把 `(0,0)` 当全地图通用回收坐标。

18. 测试与验收

18.1 纯算法单元测试

`test_return_path.py` 至少实现：

1. 直线 100 点大幅压缩，同时返回长度不大于原长度。
2. 直角路径保留安全转角和转角圆盘验证。
3. U 形墙两端近、实则隔墙，不产生跨墙捷径。
4. 任一未知格穿过候选线段时返回 `UNKNOWN`，不启用捷径。
5. 小回环删除只在端点连线安全时发生。
6. GPS 单点远跳被丢弃，不形成断裂长线。
7. 位姿方差上升使 clearance 增大；超过阈值不启新捷径。
8. map_revision 改变让当前捷径缓存失效。
9. 原始路线回退保持正确点序和 `next_index`。
10. waypoint 到达两帧才推进，横向偏离后请求处理。
11. GPS 暂不可用时保持抓取、停止无依据世界导航。
12. 空轨迹、单点轨迹、不同 frame、超过 600 点不崩溃。
13. 长于 300 px 的线段无地图证书时不被当成 Lidar 验证安全。
14. `SegmentCheck` 的 supercover 角落相邻墙格不会漏检。
15. 无奖励掉落不宣布返航成功；正奖励后才重置新出航起点。

18.2 集成与仿真测试

- Map01 长墙两侧返航：比较原始面包屑和捷径版本，
  不允许将路径压成穿墙直线。
- 多转角与窄走廊：验证载弹包络不足时主动退化。
- 返航途中被另一架无人机暂挡：观察 `BLOCKED -> FOLLOWING`
  或 `REPLAN_PENDING`，不能写入永久静态墙。
- 返航中发现新墙：旧安全证书作废，并触发原链/A* 回退。
- 语义范围内看到回收区：在近距且局部可接近后切换
  原有精确投放；记录 grasper 何时保持/释放。
- 同一固定炸弹布局至少 20 次配对运行；
  包括 Map01、Map02 和较大地图，不把测试布局写死到算法。

每回合输出以下指标：

```text
raw_point_count / compressed_point_count
raw_length_px / compressed_length_px / compression_ratio
返航逻辑步数与最后投放逻辑步数
墙体与无人机碰撞次数、健康值损失
DEGRADED_RAW 次数、BLOCKED 累计步数、INVALID 次数
A* 重规划次数、过期证书重检次数、假安全捷径次数
投放成功率（以回收正奖励计，不以 grasper 松开计）
```

首版验收：20 次配对平均返航步数有改善或持平，
投放成功率不能低于当前面包屑策略；碰撞和健康损失
不得明显增加。任何缩短路线却增加穿墙或丢弹的版本
必须关闭捷径开关。单元测试通过后运行 `./check_submission.sh`，
并检查打包 ZIP 的 `solutions/` 文件结构；文档本身不要求
运行仿真以声称已实现。

19. 分阶段实施清单

阶段 A：接口冻结。

1. 与定位负责人确认 `PoseEstimate` 方差和 frame 语义。
2. 与地图负责人确认 `SegmentCheck`、supercover、未知格
   和 revision 策略；与 A* 负责人确认 `carrying`/clearance 参数。
3. 与任务分配负责人确认抓取、DROP、verified clear 的交接。

阶段 B：原路线适配。

1. 实现 `TrailSample`、`BreadcrumbRecorder` 与 `ReturnRoute`。
2. 保持原逆序行为，验证 next waypoint 和投放结果一致。
3. 处理内存溢出、frame 断裂和跳点，不做任何捷径。

阶段 C：安全压缩。

1. 实现清洗、共线候选、小回环候选与窗口化最远可见点。
2. 仅接受 checker 的 `SAFE`，记录每条路线的证书与版本。
3. 先用合成 U 墙、未知格和转角测试，再上 Map01。

阶段 D：进度与重规划。

1. 实现偏离、卡住、动态障碍、地图更新、局部回退状态机。
2. 加入 `ReplanRequest`，A* 结果逐段复验后才能执行。
3. 用控制器 feature flag 将输出接到现有运动和精确投放方法。

阶段 E：评测和交付。

1. 固定布局至少 20 次配对比较长度、时间、健康、成功率。
2. 如捷径伤害安全或分数，回退 `clean_raw`；
   `legacy` 只保留作复现实验，不作为未经检验的安全保证。
3. 做 Python 版本、提交检查、ZIP 检查和无显示环境冒烟。

20. 尚需确认的问题

1. 机身 hull 的离线实测最大外接半径是否确实不超过 17 px？
   目前 17 来自 24×24 精灵边界保守估计；应以测试验证。
2. 抓取关节在极端速度/碰撞下，炸弹中心离机身中心的
   实际上界是多少？若 40 px 不够，必须增大或禁用捷径。
3. 地图负责人能否提供真正的“已知自由”距离场与每格
   最近更新步？否则地图证书只能更保守。
4. A* 是否已经支持按 `carrying=True` 膨胀障碍？
   如果不能，返航模块必须逐段复验，并可拒绝整个 A* 路线。
5. 定位负责人能否在 GPS 中断时保持 world frame 和
   可校准方差？若只能 local frame，世界路线必须暂停。
6. 回收区附近是否有不同地图的独特通道，需要更小的
   实测包络才能通过？不能靠降低安全半径“赌”能穿过。
7. `ReturnPathConfig` 与探索、任务分配配置由谁集中创建？
   建议统一在协调器一次性注入，避免多机权重不一致。
8. 评测器是否有额外每步运行时间限制？当前本地代码只提供
   任务时限；本方案仍需要以目标服务器实测为准。

实施边界：本任务负责轨迹记录、压缩与返航状态输出；
地图负责人负责安全线段证明，A* 负责人负责绕行候选，
协调器/控制器负责电机与 grasper，任务模块负责确认清除。
只有全部接口接线并经过仿真后，才能称它为已经跑通的算法。
