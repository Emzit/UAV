仿真分段计时指南
================

在 MobaXterm 的 SSH 终端运行以下命令。`--profile-timing` 不主动修改
地图、炸弹、控制逻辑或评分规则；但计时本身有少量开销，可能改变
90 秒内实际完成的仿真步数。

```bash
conda activate swarm
cd /data-ssd/guoyu/uav/baseline/swarm-eod
python -m swarm_rescue.launcher \
  --competition \
  --headless \
  --profile-timing \
  --stop_at_first_crash \
  -c config/competition_rescue_eval_plan.yml
```

每轮结束后，终端会出现 `Timing profile`。关闭计时只需删除
`--profile-timing`。即使有 `--headless`，Arcade/Pyglet 仍需要可用的
X11 或 Xvfb 显示服务。

若总耗时主要落在 `control`，再加 `--profile-control-detail` 做函数级
诊断；该参数也会自动启用 `--profile-timing`。建议只在定位瓶颈时使用，
因为被统计的函数可能每步调用很多次，细粒度计时本身会降低步频。

```bash
python -m swarm_rescue.launcher \
  --competition --headless --profile-control-detail \
  --stop_at_first_crash \
  -c config/competition_rescue_eval_plan.yml
```

关键字段：

- `on_update`：全部仿真更新的耗时；`avg` 是平均每步毫秒数，
  `p95` 是 95% 分位，`max` 是最慢的一步。
- `control`：10 架无人机的控制器总耗时；
  `slow_control drone N` 列出总耗时最高的 3 架无人机。
- `sensor_rays`：传感器射线的场景绘制、计算及结果读取。
- `sensor_agents`：传感器结果转为各无人机观测值。
- `physics`：Pymunk 微步；`apply_commands` 是物理步前的指令应用。
- `collect_messages` / `transmit_messages`：分别是收集、发送通信消息。
- `exploration_tracking`：官方轨迹探索统计的逐步更新。
- `state_recording`：每步保存无人机和炸弹状态到内存。
- `video_capture`：视频帧捕获；当前配置关闭视频时几乎为空。
- `on_draw`：Arcade 绘制回调；无头模式可能没有回调。
- `update_other`：未单列的更新代码及计时本身的开销。
- `round_cleanup`：结束时保存录制、截图、关闭窗口；不计入
  `on_update` 的单步统计。
- `100-step wall rates`：按 100 步统计真实墙钟步频，包括事件循环等待
  和绘制延迟；同时给出该段平均更新耗时及耗时最高的 3 个阶段，
  可找出从哪一段、哪个阶段开始变慢。

函数级模式还会输出：

- `control mode totals`：按 `explore`、`carry`、`navigate` 等控制模式汇总。
- `control detail hotspots`：按“模式/函数”列出最耗时的 15 项。
  `calls` 是调用次数；`self` 只算该函数自身，不重复计算被统计的
  子函数；`inclusive` 包含子函数，因此不同项的 `inclusive` 不能相加。
- `control detail parents`：按包含子函数的总耗时列出前 5 个调用入口，
  用来判断较慢的安全线段检测是由探索、A* 还是返航触发。
- `control_unprofiled_approx`：没有落入这些函数计时范围的控制器耗时
  估计值，也含计时包装器开销，不能当作精确的其他函数耗时。
- 每 100 步下方的 `control self`：该区间最耗时的 3 个函数自身耗时，
  便于定位后期突然变慢的具体位置。

诊断覆盖前沿搜索、A*、目标竞价、返航轨迹、地图安全线段检测、
地图扫描、定位及无人机控制模式。没有列出的逻辑仍包含在上层
`control` 中，因此函数级细目之和不一定等于 `control` 总耗时。

这些是墙钟时间，不是 CPU 使用率；OpenGL 同步等待也可能计在
`sensor_rays` 中。先比较各阶段的总耗时和每 100 步的速率，再决定
优化控制器、传感器运行环境还是录制。计时本身有少量开销，因此
最终得分对比应关闭 `--profile-timing`，在相同场景下多跑几轮。
